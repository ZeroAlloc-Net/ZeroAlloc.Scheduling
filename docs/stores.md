# Backends

ZeroAlloc.Scheduling separates the job execution engine from the persistence layer. The engine (`SchedulingWorkerService`) talks to `IJobStore`. Four store implementations are provided; pick one per application.

## InMemory

Best for development, testing, and single-instance applications that don't need job persistence across restarts.

```bash
dotnet add package ZeroAlloc.Scheduling.InMemory
```

```csharp
services.AddScheduling()
        .WithInMemoryStore()
        .AddMyJob();
```

Jobs are stored in memory inside the process. All state is lost on restart.

Finished jobs (Succeeded and DeadLetter) stay in the store, as they do in the other backends, so the dashboard can count, list and requeue them. Delete one through the dashboard or `IJobDashboardStore.DeleteAsync` to free it. A poll only looks at Pending, Failed and Running jobs, so its cost does not grow with the number of finished jobs, but memory does.

## EF Core

Persist jobs to any database supported by EF Core (SQL Server, PostgreSQL, SQLite).

```bash
dotnet add package ZeroAlloc.Scheduling.EfCore
```

```csharp
services.AddScheduling()
        .WithEfCore(opt =>
            opt.UseSqlite("Data Source=jobs.db"))
        .AddMyJob();
```

The store uses `SchedulingDbContext`. Apply the migration before first run:

```bash
dotnet ef migrations add InitScheduling --context SchedulingDbContext
dotnet ef database update --context SchedulingDbContext
```

`FetchPendingAsync` uses an atomic `ExecuteUpdateAsync` pattern (EF Core 7+) to claim jobs without loading them first, preventing double-dispatch under concurrent workers.

### Enqueueing through the outbox

`WithOutboxWriter<TJob>()` registers an `IOutboxWriter<TJob>` that writes a job into the [ZeroAlloc.Outbox](https://outbox.zeroalloc.net) store inside the same `DbTransaction` as your business write, so the job and the business row commit or roll back together.

The writer needs an `IOutboxStore` and an `IOutboxSerializer`. Since ZeroAlloc.Outbox 4.0, `AddOutbox()` no longer falls back to a serializer, so choose one explicitly. Prefer the AOT-safe one, described in [AOT-Safe Serialisation](https://outbox.zeroalloc.net/cookbook/06-aot-serialisation):

```csharp
using System.Text.Json.Serialization;
using ZeroAlloc.Serialisation;

[ZeroAllocSerializable(SerializationFormat.SystemTextJson)]
public sealed record SendInvoiceJob(int InvoiceId);

[JsonSerializable(typeof(SendInvoiceJob))]
internal sealed partial class SendInvoiceJobJsonContext : JsonSerializerContext;
```

```csharp
// Trim- and AOT-safe: generated by ZeroAlloc.Serialisation, which ZeroAlloc.Outbox depends on.
services.AddSerializerDispatcher();

services.AddOutbox().WithEfCore<AppDbContext>();   // from ZeroAlloc.Outbox.EfCore

services.AddScheduling()
        .WithEfCore(opt => opt.UseSqlServer(connectionString))
        .WithOutboxWriter<SendInvoiceJob>();
```

If you would rather not annotate job types, opt in to reflection-based System.Text.Json instead. It produces the same bytes the Outbox 3.x fallback did, and it warns with `IL2026` and `IL3050` at this call in a trimmed or NativeAOT build:

```csharp
services.AddOutbox()
        .WithEfCore<AppDbContext>()
        .WithSystemTextJsonSerializer();
```

With neither, resolving `IOutboxWriter<TJob>` throws an `InvalidOperationException` that names both options. See the Outbox guide [Migrating to v4](https://outbox.zeroalloc.net/migrating-to-v4) for the other 4.0 changes, such as one outbox store per container.

## ORM

Persist jobs through [ZeroAlloc.ORM](https://github.com/ZeroAlloc-Net/ZeroAlloc.ORM): raw SQL with compile-time parameter binding, no change tracker and no runtime reflection. Supports SQLite, PostgreSQL and SQL Server, and is NativeAOT compatible.

The package targets **net10.0 only**, because ZeroAlloc.ORM ships for net10.0 only. On net8.0 or net9.0, use the EF Core store.

```bash
dotnet add package ZeroAlloc.Scheduling.Orm
dotnet add package Microsoft.Data.Sqlite   # or Npgsql, or Microsoft.Data.SqlClient
```

### Registration

`WithOrm()` does not register a connection. Register a scoped `IAsyncDbConnection` yourself, since the connection's lifetime, provider and connection string belong to the application. `AsAsync()` from `System.Data.Async.Adapters`, which comes with the package, wraps any ADO.NET connection. The store opens it on first use.

```csharp
using System.Data.Async;
using System.Data.Async.Adapters;
using Microsoft.Data.Sqlite;
using ZeroAlloc.Scheduling.Orm;

services.AddScoped<IAsyncDbConnection>(_ =>
    new SqliteConnection("Data Source=jobs.db").AsAsync());

services.AddScheduling()
        .WithOrm()
        .AddMyJob();
```

`WithOrm()` uses the SQLite query spelling. For another database, pass its `OrmSchedulingDialect`:

| Database | Registration | Schema source | Migration dialect |
|----------|--------------|---------------|-------------------|
| SQLite | `WithOrm()` or `WithOrm(OrmSchedulingDialect.Sqlite)` | `SchedulingOrmMigrations.Sqlite` | `SqliteMigrationDialect` |
| PostgreSQL | `WithOrm(OrmSchedulingDialect.Postgres)` | `SchedulingOrmMigrations.Postgres` | `PostgresMigrationDialect` |
| SQL Server 2012+ | `WithOrm(OrmSchedulingDialect.SqlServer)` | `SchedulingOrmMigrations.SqlServer` | `SqlServerMigrationDialect` |

Only the claim query and the recurring-job insert differ between dialects. The claim is bounded with `LIMIT` on SQLite and PostgreSQL and with `OFFSET … FETCH NEXT` on SQL Server. The recurring insert uses `ON CONFLICT DO NOTHING` on SQLite and PostgreSQL, and `INSERT … WHERE NOT EXISTS` under an update range lock on SQL Server. Everything else is plain ANSI SQL.

#### A connection of its own

If the application already registers an unkeyed `IAsyncDbConnection` for its own data, keep the jobs on a separate database by registering a keyed connection and passing its key:

```csharp
services.AddScoped<IAsyncDbConnection>(_ => OpenAppDb());                     // the application's data
services.AddKeyedScoped<IAsyncDbConnection>("jobs-db", (_, _) => OpenJobsDb()); // the job store

services.AddScheduling()
        .WithOrm(OrmSchedulingDialect.Postgres, connectionKey: "jobs-db")
        .AddMyJob();
```

The store then resolves only the connection registered under that key and never falls back to the unkeyed one; without a keyed registration, resolving the store throws. Apply the schema to the keyed database. As with the other overloads, an `IJobStore` you registered earlier wins.

### Schema

The store does not create tables on the fly. Apply the schema with ZeroAlloc.ORM's `MigrationRunner` before the host starts:

```csharp
using ZeroAlloc.ORM.Migrations;

var connection = new SqliteConnection("Data Source=jobs.db").AsAsync();
await using (connection)
{
    await connection.OpenAsync(ct);
    await new MigrationRunner(connection, SchedulingOrmMigrations.Sqlite, new SqliteMigrationDialect())
        .RunAsync(ct);
}
```

Use the schema source and migration dialect from the table above for PostgreSQL or SQL Server. The runner records applied versions under the name `ZeroAlloc.Scheduling`, so the job schema can share a history table with your own migrations without version numbers colliding. Running it again applies only what is missing, so it is safe to call on every startup.

It creates a `SchedulingJobs` table with an index on `(Status, ScheduledAt)` for the poll, one on `ClaimToken` for the claim read-back and a unique one over the live runs of recurring jobs. Finished jobs are kept, not deleted, so without the first index every poll would scan the whole table.

`FetchPendingAsync` claims jobs with a single `UPDATE` that stamps a fresh claim token, then reads back by that token. The `UPDATE` checks the status again on each row it takes, so a worker that waited for another's row lock takes nothing, and concurrent workers never dispatch the same job twice.

A recurring job has at most one live run, one that is Pending, Running or Failed. Version 3 of the schema adds a unique index over the live runs of recurring jobs, so instances that start at once seed one run, and a restart never revives a completed run. Releases before 2.5 could leave several live runs of one recurring job; version 3 first deletes all but the earliest. When the job's live run is Pending, a new seed updates its payload and attempts, and moves its due time only if the schedule changed.

### Compared with EF Core

- **No dashboard.** The ORM store implements `IJobStore` only and registers no `IJobDashboardStore`, so the dashboard cannot be pointed at it. Use the EF Core or Redis store if you need the dashboard.
- **No outbox writer.** `WithOutboxWriter<TJob>()` is part of the EF Core package.
- **Not interchangeable on disk.** The ORM store writes to `SchedulingJobs` with native date types; EF Core writes to `ScheduledJobs` with dates stored as ticks. Moving between them means draining the queue, not repointing the store at the old table.
- **Lighter.** No `DbContext`, no change tracker and no EF Core dependency, which keeps a NativeAOT app smaller.

## Redis

For distributed deployments with multiple worker instances.

```bash
dotnet add package ZeroAlloc.Scheduling.Redis
```

```csharp
services.AddScheduling()
        .WithRedis("localhost:6379")
        .AddMyJob();
```

Jobs are stored as Redis hashes. The store maintains three tracking Sets (`jobs:succeeded`, `jobs:failed`, `jobs:deadletter`) for O(1) summary queries without scanning all keys.

> **Upgrade note.** Hash keys are now derived from `JobId.ToString()`, a 26-character ULID base32 string, instead of the previous `Guid` representation. Live deployments must drain the queue (let in-flight jobs complete and stop producing new ones) before upgrading: existing keys written by the older version will not be discovered by the new lookups, so they should be allowed to finish or be cleared explicitly before the rollout.

## Abandoned runs and `ClaimTimeout`

A host that stops or crashes while a job runs records no outcome, so the job stays Running. Every store claims such a job again once its start is older than `SchedulingOptions.ClaimTimeout`, 15 minutes by default, and counts that claim as a new attempt. When the abandoned run was the job's last attempt, the worker dead-letters the job instead of running it, and schedules the next occurrence if the job is recurring.

The timeout cannot tell a stopped run from a slow one. It counts from the poll that claimed the job, and the worker runs a poll's jobs in turn, so a job's wait for the jobs claimed before it counts too. **A job that is not done within `ClaimTimeout` is claimed again while it still runs, so it runs twice.** Set the timeout above the longest batch you expect, up to `BatchSize` runs in a row, and keep jobs idempotent.

A poll takes expired claims before due jobs, so a busy queue cannot keep an abandoned job waiting. Redis keeps the Running jobs in a `jobs:claims` sorted set by claim start, in milliseconds; the first poll of a store adds jobs that were already Running before the upgrade.

When the slow run finishes after all, its outcome must not overwrite the run that took the job over. Stores that stamp each claim with a token record an outcome only while the job still holds the claim the run started with:

| Store | Outcome of a run that lost its claim |
|---|---|
| EF Core | Ignored. The store is scoped, so each poll has its own claims. |
| ORM | Ignored. The store is scoped, so each poll has its own claims. |
| Redis | Ignored when another host took the job over. Workers in one process share the singleton store, and there the late outcome is recorded. |
| InMemory | Recorded. One instance serves every worker. |

### Recurring jobs get their live run back

The worker writes a recurring job's next occurrence in a write of its own, after the outcome of the run before it: after a dead-letter in every store, and on the ORM store also after a success. When that write fails, for example on a transient store error, the job has no live run left. And a run that lost its claim can seed the job with the definition it started with, which on the ORM store rewrites the Pending next occurrence.

So the hosted service generated for a recurring job seeds it again every `ClaimTimeout` while the host runs, with the job's current definition: its payload, schedule and maximum attempts. The seed does nothing while the job has a live run, so repeating it is safe. A lost next occurrence comes back within one `ClaimTimeout`, without a restart. On the ORM store the seed also puts the current definition back on a Pending run; the InMemory, EF Core and Redis stores leave a Pending run as it is. A repeat that fails is logged as an error and tried again one `ClaimTimeout` later. Only the seed at startup fails the host start. A `ClaimTimeout` above about 49 days, the longest delay `Task.Delay` accepts, re-seeds every 49 days instead.

A custom `IJobStore` should claim an expired Running job again in `FetchPendingAsync` as well. Otherwise a recurring job whose run was abandoned never runs again.

## Dashboard Integration

The InMemory, EF Core and Redis stores also implement `IJobDashboardStore`, which powers the dashboard API. EF Core and Redis register `IJobDashboardStore` automatically. InMemory implements it directly on `InMemoryJobStore`. The ORM store does not implement it, so a dashboard cannot run on it.

If you implement a custom store, register `IJobDashboardStore` explicitly:

```csharp
services.TryAddScoped<IJobDashboardStore>(sp =>
    (IJobDashboardStore)sp.GetRequiredService<IJobStore>());
```

## Choosing a Backend

| Requirement | Recommended backend |
|-------------|---------------------|
| Local development / unit tests | InMemory |
| Single-server with persistence | EF Core (SQLite or SQL Server) |
| Persistence under NativeAOT, no dashboard needed | ORM (net10.0) |
| Multi-server / distributed | Redis |
| Custom / existing database | Implement `IJobStore` + `IJobDashboardStore` |
